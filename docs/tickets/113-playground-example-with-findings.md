# TICKET-113: Playground: an example that shows findings

**Phase:** 8 — Token Engine Overhaul, Epic 7b (playground)
**Priority:** Medium
**Effort:** S
**Blocked by:** 077
**Status:** done (pending the GitHub run)
**Spec:** [playground](../specs/playground.md) (decision 6)

## Problem

The one-click example (brand-ab) lints clean, so a visitor never sees what a finding looks like, which is the point of the tool (noticed on the 077 screenshots, 2026-10-19).

## What to build

A second example, "Example with problems", next to "Load example": brand-ab with a few deliberate flaws that the default rules catch (e.g. a semantic token with a raw value instead of an alias, a broken alias, a duplicate value, a contrast pair that fails), so the findings list, the structure table and (later) the graph's redlines all have something to show. Kept as a fixture in `test/fixtures/` so its findings are checked against `dta lint` output, not written by hand.

## Acceptance criteria

- [x] Fixture with deliberate flaws; a test checks the playground's findings equal `dta lint` on it
- [x] "Example with problems" button in `TokenInput` (story updated), bundled like brand-ab (no request)
- [ ] All gates pass plus the site job, and the GitHub run is green (gates and site job green locally; GitHub run pending, nothing pushed)

## Outcome

Giving the example its own config would mean a second lint mode in the playground that a visitor's own files never get, and a Lint view that lists rules depending on the example; so the example uses one flaw per **built-in** rule instead, and every rule row of the Lint view has something to open. Configurable rules in the playground (toggling rules, a pasted config) stay out of scope, as the spec says.
