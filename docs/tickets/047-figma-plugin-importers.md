# TICKET-047: Figma: documented input format, schema and adapters

**Phase:** 8 — Token Engine Overhaul, Epic 3 (@dta/figma)
**Priority:** Medium
**Effort:** M
**Blocked by:** TICKET-040
**Status:** done
**Spec:** [figma-package](../specs/figma-package.md) (decision 11)

## What to build

Make "where do I get the file without the Enterprise API" a user-land concern: DTA documents and validates its own input format, publishes a schema for it, and keeps third-party export formats in small removable adapters.

## Acceptance Criteria

- [x] A Zod schema for the one-file-per-mode DTCG file (tokens, groups, `$type`/`$value`, `$description`, `com.figma` extensions); a JSON Schema generated from it is committed (or generated by a script and checked in CI); both fixtures validate
- [x] Docs page (in `docs/`) describing the format and listing ways to obtain it (Enterprise REST API, a plugin of the user's choice plus conversion, Figma's native export when available) as guidance, without endorsing or depending on one plugin; CLAUDE.md's "compatible plugins" list is reworded accordingly
- [x] `importPluginExport(json)` returns `{ format, model, diagnostics }` for adapters registered in one place; input is validated with Zod at the entry, a wrong shape yields a diagnostic naming the failing path, never an exception
- [x] The tokenHaus adapter (legacy `importers/tokenhaus.ts` and `detect.ts` behaviour, including `detectFormat`) is ported as one isolated adapter file with its legacy test cases re-expressed through the public API; removing it requires touching nothing else
- [x] Unknown formats produce a diagnostic that points to the format documentation
- [x] 039 parity table: importers and `pull --from-file` rows updated, including the keep-or-drop decision for the tokenHaus adapter
- [x] All gates pass, and the GitHub run is green

## Implementation notes

- Schema: `packages/figma/src/token-file-schema.ts` (`tokenFileSchema`, `tokenFileJsonSchema()`). It lives in `@dta/figma` because that is where Zod is a dependency; core keeps its hand-written validation (precise diagnostics). Both fixtures validate. The JSON Schema is committed as `docs/token-files/token-file.schema.json`, generated by `pnpm run schema:generate`, and a test fails when it is stale (no extra CI step needed).
- Docs: `docs/token-files/input-format.md` (format, schema, ways to obtain the file, adapters). CLAUDE.md "Compatible Figma plugins" and the README plugin sentence are reworded to say DTA depends on no plugin.
- API: `importPluginExport(json)` → `{ format, model, diagnostics }` and `detectFormat(json)`. Input is checked with Zod first. Diagnostic codes: `invalid-export` (not a JSON object), `unknown-format` (names the docs page), `native-format` (input is already per-mode DTCG and has no file name to read it under), `invalid-collection-name` (adapter: collection name contains a dot). Everything else comes from core's `parseTokenFiles`.
- Adapters: `packages/figma/src/adapters/` with `types.ts` (the `Adapter` interface), `tokenhaus.ts` and `index.ts` (the one list). Removing tokenHaus is deleting `tokenhaus.ts` and its entry in `index.ts`. The adapter converts to per-mode file inputs that core parses, so the result is a normal model.
- Real export check: `docs/token-files/design-tokens-daisyui.json` converts to the same 22 collections and 41 collection/mode files as the legacy daisyUI fixture; every serialized file validates against the schema.
- Legacy `tokenhaus.test.ts` and `detect.test.ts` cases are re-expressed through the public API. Root `package.json` now depends on `@dta/figma` so the schema script can import it by name.
- 039: keep-or-drop decision recorded in the parity table (keep until Epic 6 parity work).
