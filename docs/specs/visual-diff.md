# Spec: `dta diff` — token-aware visual regression, on your own infrastructure, reviewed in the pull request

**Status:** approved (2026-10-16); open questions below are settled in the tickets that need them
**Part of:** [Token Engine Overhaul](./token-engine-overhaul.md), Epic 8
**Depends on:** Epic 7 ([website](./docs-site.md): its component stories are the first target), Epics 2–6
**Design sources:** concept doc "Visual Regression Module — Concept Sketch" (sections Final phase: visual-diff, pipeline, capabilities, token-aware review and inspect); design system **DTA Drafting Table** (DiffCard, Redline, signal tokens); landing mockup "J · Drafting Table" (See it section, drag-to-compare slider)
**Related:** TICKET-023 (v1 Playwright tests, retired here), [cli-parity spec](./cli-parity.md) decision 10

## Problem

One colour change touches a hundred stories, and nobody reviews a hundred screenshots. Token changes are reviewed as JSON diffs, component changes as code diffs, and their visual effect is seen only after release. SaaS tools such as Chromatic show pixel changes, but they do not know which token caused them, and they send screenshots of unreleased UI to someone else's cloud. v1's `test:visual` (four hand-written HTML pages, baselines that are not even in the repo, not in CI) does not help either.

## Solution

`dta diff` renders the project's stories twice, at the base (default: merge base with the default branch) and at the head, in the same run, compares them pixel by pixel and explains the differences by token: "color.action 600 → 700 explains 96 of 100 changed stories; 4 are unexplained". It runs entirely in local Node processes, Docker or self-hosted CI runners. In GitHub it reports as a status check plus one pull-request comment that updates in place, with the full report (baseline, candidate, diff, slider) as a static page.

## Decisions

1. **Command:** `dta diff` (maintainer decision; the landing page already shows `npx dta check && npx dta diff`). `dta check` (structure and breaking changes) and `dta inspect` are separate later epics.
2. **No stored baselines** (maintainer decision). The baseline is rendered from the base ref in the same run: DTA creates a temporary worktree at the base, runs the project's configured build there and for the head, serves both outputs and captures both. Consequences: no images in git or artifacts to manage, works in private repos, identical environment for both sides, and any change (token or component code) is caught. "Approval" marks a reviewed head commit (label or check action), it does not update files.
3. **Stories, adapter-based.** A story is a URL to a static page plus the viewports to capture. Version 1 ships one adapter: static sites (the DTA website's component story pages from Epic 7, read from a stories manifest the site build writes). The adapter interface is designed so a Storybook adapter (reading `index.json` of a static Storybook build) follows as the next ticket after this epic.
4. **Config:** a `diff` section in `dta.config.*`: build command, output dir, stories source (adapter + options), viewports, thresholds, base ref. Validated by the config schema like everything else.
5. **Rendering:** Playwright Chromium, optional peer dependency loaded only by `dta diff`. Deterministic environment: pinned browser, fonts served by the site (no system fonts), animations and transitions disabled, `prefers-reduced-motion`, network idle before capture. An official container image (Docker) bundles Node, Chromium and DTA for local and self-hosted use.
6. **Comparison:** pixelmatch-style perceptual diff per story × viewport: diff image with high-contrast overlay and the exact changed-pixel ratio. Thresholds configurable globally, per viewport and per story group.
7. **Token change set:** `diffTokens(base, head)` lists added, removed and changed tokens per brand and mode with resolved values before and after (alias changes expand to the tokens they affect). Useful on its own (`dta diff --tokens-only`, markdown/JSON) and the input for attribution.
8. **Token attribution:** while rendering, DTA records which CSS custom properties resolve on each element (computed from the stylesheet and DOM, not guessed). Changed pixel regions are mapped to elements and their variables, then to the token change set. Each changed story is **explained** (all changed regions trace to changed tokens) or **unexplained**. Feasibility is the first thing to prove (spike ticket), because it decides how far "review by token" goes in version 1. **Where a token is put back ([TICKET-111](../tickets/111-diff-attribution-scoped-example.md), maintainer decision):** under the selectors `dta build` writes and under every rule in the rendered page's own stylesheets that declares the token's custom property (same selector, inside the same `@media`/`@layer`/`@supports`/`@container`/`@scope`/nesting, `!important`), so CSS re-scoped per wrapper or component is explained without configuration. With several brands, a re-scoped rule counts for the brand whose head value it declares, and not when two brands share that value. Inline `style` declarations and cross-origin sheets stay unexplained. A `diff.attribution.selectors` config was considered and not built.
9. **Review by cause:** the report groups explained changes by token (a few representative samples and a contact sheet per token change) and lists unexplained changes one by one. Thresholds by cause: explained changes need one review per token change; unexplained changes above threshold fail the check until reviewed.
10. **Portable output, hosting is user land** (maintainer decision). `dta diff` writes one self-contained report folder that works from any static host or straight from disk: `index.html` (Drafting Table design: baseline, candidate, diff overlay, drag-to-compare slider, redline labels naming tokens), PNGs and thumbnails, `summary.md` (for PR comments and agents) and `result.json` (stable, versioned schema, for CI and agents). All links inside are relative. DTA contains no provider-specific code: it does not know Vercel, GitHub Pages or any other host.
11. **Publish hook.** `diff.publish` in the config (or `--publish <command>`) names a command DTA runs on the report folder after a run, for example a Vercel deploy, a push to an assets branch or an `rsync` to an internal server. The command gets the folder path (argument and `DTA_REPORT_DIR`) and prints the public base URL as its last stdout line (or a regex/JSON path configured in `diff.publish.url`). DTA then rewrites `summary.md` with absolute thumbnail and report links and records the URL in `result.json`. A failing hook fails loudly but never hides the diff result. Without a hook, `summary.md` has no images and links to the local report.
12. **GitHub integration is a thin layer.** A composite action (and an example workflow) runs `npx dta diff` (with whatever publish hook the project configured), then posts a status check (pass / changes to review / fail by threshold) and one sticky comment with `summary.md`: the explained-by-token summary, a table per story and viewport with change ratios and baseline / candidate / diff thumbnails when a publish URL exists, and a link to the full report. Without a publish hook the report is uploaded as a workflow artifact and the comment says so. Approval: a label (for example `dta-diff-approved`) on the head commit turns "changes to review" into pass; a new push needs a new review. Experience in the spirit of Chromatic (status check, hosted review page, approval), but rendered in the user's CI, nothing stored, explained by token, and hosted wherever the user publishes.
13. **Recipes, not integrations.** The docs ship copy-paste publish hooks: Vercel (preview deployment of the report folder; DTA's own repository uses this), a GitHub assets branch (no extra service; images rendered via `github.com/…/raw/…`, cleaned up when the PR closes), and a generic static server (on-premise).
14. **Dogfooding:** the DTA website's CI runs `dta diff` on its own stories from the first working ticket on; its token files are the first real test.
15. **`test:visual` is retired** at the end of the epic (directory, scripts, root Playwright dev dependency if unused, the `dta test:visual` stub; v2 is unreleased, so no deprecation period).

## Open questions (need a maintainer call before the tickets start)

1. **Attribution fallback:** if per-element variable recording proves unreliable for some CSS (shorthands, `calc()`, inherited values), is a coarser attribution acceptable for version 1 (story-level: "this story uses changed tokens X, Y") with element-level later? Recommended: yes. **Settled by [TICKET-083](../tickets/083-diff-attribution-spike.md):** element-level attribution works for version 1 by reverting each changed token to its base value in the head page and recording which elements' computed styles or boxes change (shorthands, `calc()`, inheritance, alias chains and modes covered; values built as literals or read by JavaScript stay unexplained). Story-level summaries come from the same data.
2. **Approval granularity:** version 1 approves a whole PR head; approving per token change (concept: "approve one token change across all affected stories") as a follow-up. Agree?
3. **Container image:** publish to GitHub Container Registry with the release, or document a Dockerfile only for version 1? Recommended: Dockerfile first, published image with the first release.

## Testing decisions

- Package seam (`@dta/visual-diff`, internal): token change sets on crafted models and a fixture pair; image comparison on small synthetic PNGs; attribution on fixture pages with known variable usage; report rendering from a fixed result (HTML structure, markdown, JSON schema).
- CLI seam: snapshot scenario `diff-tokens` (markdown, no browser) on a fixture pair, recorded with `pnpm snapshot:record`; worktree base resolution against a temporary git repository.
- End-to-end: a CI job in the container renders a small fixture site at two commits (one token change, one component change) and asserts which stories differ and which are explained; plus the dogfood run on the website.
- Images never go into snapshots (renderer-dependent).

## Out of scope

Built-in hosting or provider SDKs (publishing is the user's hook), Storybook adapter (next ticket after this epic), `dta inspect` (token inspector, brand × theme grid, drift finder, contrast, coverage), `dta check` and `dta audit`, GitLab/Bitbucket, a hosted service, mobile renders, comparing Figma with code.
