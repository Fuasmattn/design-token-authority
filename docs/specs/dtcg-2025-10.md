# Spec: Read DTCG 2025.10 token files and resolver documents

**Status:** done (approved 2026-10-21; tickets 132–138 done 2026-10-22)
**Replaces:** the "What to build" plan in [TICKET-094](../tickets/094-dtcg-2025-10-conformance.md)
**Related:** [TICKET-032](../tickets/032-native-figma-dtcg-migration.md) (Figma's native DTCG export), [TICKET-016](../tickets/016-multi-brand-composition.md) (multi-brand composition), [TICKET-116](../tickets/116-motion-tokens-and-transitions.md) (motion tokens stored as `string` because `duration`/`cubicBezier` were missing), [core-token-model](./core-token-model.md)
**Sources:** [DTCG 2025.10](https://www.designtokens.org/TR/2025.10/): [Format](https://www.designtokens.org/tr/2025.10/format/), [Color](https://www.designtokens.org/tr/2025.10/color/), [Resolver](https://www.designtokens.org/tr/2025.10/resolver/) (Final Community Group Report, 28 October 2025)

## Problem

DTA reads DTCG in the shape of Figma variables: one `{Collection}.{Mode}.json` file per collection and mode, four types (`color`, `number`, `string`, `boolean`) and scalar values. The stable DTCG 2025.10 report goes further, and tools are starting to write it (Figma's native export is announced for late 2026). A valid 2025.10 file fails in DTA today:

- a token without its own `$type` is `missing-type`, because group `$type` is ignored (`readEntries` in `packages/core/src/entries.ts` skips every `$` key on groups);
- a colour object (`{ colorSpace, components, alpha?, hex? }`) is `invalid-value`;
- `dimension`, `duration`, `fontFamily`, `fontWeight`, `cubicBezier` and the composite types are skipped as `unsupported-type`;
- `$ref`, `$root` and `$extends` are not resolved;
- `.tokens` / `.tokens.json` files and `*.resolver.json` documents are not read (`readTokenDir` reads `*.json` only, and `X.tokens.json` would parse as collection `X`, mode `tokens`).

The goal is that **a valid DTCG 2025.10 token set works in DTA without conversion**: read, linted, built, diffed and queried, with clear diagnostics for what a target (Figma, a CSS property) cannot hold.

## What changes, by package

| Package                                        | Today                                                                           | After                                                                                                                                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@dta/core`                                    | 4 types, scalar `TokenValue`, alias = `"{a.b}"` string, collection × mode model | All 2025.10 types; structured values; group `$type`, `$deprecated`, `$root`, `$extends`, `$ref`, aliases inside composite values; a resolver reader that produces the same model  |
| `@dta/build`                                   | Style Dictionary leaves of scalars; DTCG transforms configured but never fire   | Structured values reach Style Dictionary, so `size/rem`, `color/css`, `cubicBezier/css`, `shadow/css/shorthand`, `typography/css/shorthand` … apply; outputs per modifier context |

## Decisions

1. **One model, two readers.** Per-mode files and 2025.10 files (with or without a resolver) are read into the same `TokenModel`, so every command works on both without knowing where the tokens came from. The existing per-mode format stays fully supported; nothing a user has today breaks.

2. **Per-mode files get the 2025.10 features too.** They are DTCG files: group `$type`, structured values, all types, `$ref`, `$root` and `$extends` work in `{Collection}.{Mode}.json` files as well. Existing snapshots stay unchanged, because existing files use none of it.

3. **Values are stored as written, typed.** `TokenValue` becomes a union per type: the colour object, `{ value, unit }` for `dimension` and `duration`, `string | string[]` for `fontFamily`, `number | keyword` for `fontWeight`, the four numbers of `cubicBezier`, and objects or arrays for the composites, whose sub-values may be aliases or `$ref`. A hex string stays a valid `color` value (the format DTA writes today). Core exports one `formatValue` and one `sameValue`, and every consumer uses those instead of `String(value)` and `===`.

4. **Types follow the report exactly.** Type order: own `$type`, then the type of the alias target, then the closest group `$type` (after `$extends`); never inferred from the value. An undeterminable type stays `missing-type` (error). An unknown `$type` is an error, not a warning.

5. **References: curly aliases and `$ref`, both resolved late.** Curly aliases target whole tokens; `$ref` (JSON Pointer) may target sub-values (`#/colors/blue/$value/components/0`). Both are kept unresolved in the model and resolved when a value is needed, like aliases today. Cycles are reported for every token in the cycle. `$ref` stays within the token set (no remote URIs).

6. **`$extends` and `$root` are expanded at read time.** `$extends` is a deep merge where a local token replaces the inherited one entirely; `$root` is an ordinary token named `$root` (`{color.accent.$root}`). After reading, the model holds the expanded groups; the source tree keeps the original for writing back.

7. **A resolver document maps onto collections and modes.**
   - Every **set** becomes a single-mode collection, named after the set.
   - Every **modifier** becomes a multi-mode collection, named after the modifier, with one mode per context; `default` becomes the collection's default mode.
   - A token a context overrides moves into the modifier's collection with a value per context; contexts that do not override it keep the value from the sets before it in `resolutionOrder`.
   - A token overridden by two modifiers (for example brand and theme) is the hard case; see decision 8.
   - The name uniqueness DTA relies on holds after flattening, because the report itself flattens to one token tree per input.

8. **Several modifiers at once: modes as axes.** A token's values are keyed by the contexts of every modifier that touches it, not by one mode. The model gains "axes" (one per modifier or multi-mode collection) and resolution takes a context per axis, which is what `ModeSelection` already almost is. This also delivers the earlier decision that Brand × Theme × Breakpoint should combine freely. The alternative, resolving one full token tree per permutation and keeping the model per mode, is simpler in core but multiplies outputs (4 × 3 × 2 contexts = 24 trees) and loses which modifier caused a value.

9. **Build: CSS uses the cascade, resolved outputs use permutations.**
   - CSS keeps aliases as `var()` and writes each modifier's overrides under its own attribute selector (`[data-brand="a"]`, `[data-theme="dark"]`), in `resolutionOrder`. Equal specificity plus source order gives "later wins", exactly the resolver's rule, and `var()` resolves aliases after the cascade, like the resolver resolves after flattening.
   - Outputs with resolved values (`base.css`, JS, Tailwind v3) are written per permutation, only for the combinations listed in the config, not all of them by default.
   - Composite types become CSS shorthands (`box-shadow`, `font`, `transition`, `border`) through Style Dictionary's DTCG transforms. Slice 1 checks whether Style Dictionary 4 handles 2025.10 value objects or needs an upgrade.

10. **Colours keep their colour space in CSS.** An sRGB colour is written as hex, as today; any other space is written with the matching CSS function (`oklch()`, `color(display-p3 …)`) and no silent conversion. Contrast checks and Figma convert to sRGB (gamut-mapped), and say when the result was clipped.

11. **Figma: push what variables can hold, skip the rest loudly.** Figma variables hold colour, number, string and boolean. `dimension` in `px` pushes as a number; other units, and all composite types, are skipped with one `not-pushable` warning per token. Non-sRGB colours push as their sRGB conversion, with a warning when clipped. `dta pull` keeps writing per-mode files.

12. **Files and the config.** `tokens.dir` also reads `*.tokens` and `*.tokens.json` (one single-mode collection per file, named after the file) and `*.resolver.json`. A resolver document is found automatically when `tokens.dir` holds exactly one `*.resolver.json`; `tokens.resolver: 'tokens/app.resolver.json'` in the config names one explicitly and wins; several without a config entry are an error that lists them. The resolver then decides which files belong to the set, and stray files are a warning. `brands` stays the word for the brand modifier's contexts; a new `modifiers` key selects contexts of other modifiers for the resolved outputs.

13. **Writing back keeps the source.** `serializeTokenFiles` already edits the source tree in place. Structured values, `$extensions` the tools do not know and `$extends` groups are kept as written; only changed `$value`s are rewritten. `dta push` never writes token files, so this matters for `pull` merges and future editing commands.

## Slices

Each slice is one ticket, keeps all gates green and leaves the docs current. Order: 1 → 2 → 3 → 4 → 5 → 6; 7 can follow 3.

1. **All types and structured values in core** (L): types, value union, `formatValue`/`sameValue`, validation per type with `invalid-value` messages naming the rule, group `$type` and `$deprecated`, name rules (no `{`, `}`, `.`; not starting with `$`). Consumers switched to `formatValue`/`sameValue` so nothing prints `[object Object]`. Style Dictionary check (decision 9).
2. **References** (M): `$ref` in values and sub-values, aliases inside composites, `$root`, `$extends`, cycles; graph and `dta graph` show sub-value references.
3. **Build, lint, diff, queries, audit on the new types** (L, split by package if needed): CSS shorthands for composites, colour spaces in CSS, units, Tailwind keys for the new types, contrast in any colour space, `dta token get/find` and `dta audit` with units.
4. **`.tokens` files** (S): file discovery and naming, single-mode collections, playground accepts them.
5. **Resolver documents** (L): reader, validation with the report's error list, mapping to collections and modes (decision 7), `tokens.resolver` in the config.
6. **Several modifiers at once** (L): axes in the model, resolution per context combination, CSS by cascade and resolved outputs per selected permutation (decisions 8, 9); `dta diff` and the playground pick contexts per axis.
7. **Figma push for the new types** (M): decision 11, with the push report listing what was skipped.

Done for each slice: the "Where DTA differs" list on the Learn DTCG page shrinks, the Token files reference and the published JSON Schema grow, and a fixture made from the report's own examples covers it.

**Fixture:** `test/fixtures/dtcg-2025` with one file per feature, taken from the report's examples where possible, and a resolver document with two modifiers (brand × theme). New CLI scenarios on it are recorded by name; existing snapshots must not change.

## Settled questions

Decided by the maintainer on 2026-10-21.

1. **Release scope: all seven slices go into the first npm release** (TICKET-090 waits for them). A valid 2025.10 token set, including resolver documents with several modifiers, works from the first published version.
2. **Several modifiers: axes in the model** (decision 8), with CSS by cascade and resolved outputs per selected permutation (decision 9).
3. **Wide-gamut colours keep their colour space in CSS** (decision 10); sRGB stays hex.
4. **Resolver discovery: automatic when there is exactly one**, the config overrides, several without a config entry are an error (decision 12).
