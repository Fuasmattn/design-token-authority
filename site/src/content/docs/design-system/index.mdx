DTA Drafting Table is the design system of this website, the `dta diff` reports and the playground. It looks like a drafting table: warm paper, blueprint blue, ink outlines and orange redlines that measure what changed. Its dark mode, Graphite, is the dark side of the same paper. Since the landing redesign the paper is one plain surface with a gravity well drawn on it: everything on the page gravitates towards the token.

It is also a demo of DTA itself: the tokens are DTA token files in `site/tokens`, linted with `dta lint` and built with `dta build` into the CSS this page uses. The token pages read the same files through `@dta/core`.

## Principles

1. **Measure, don't decorate.** The signature element is the redline: a `stroke-redline` line in `signal-bg` with a mono label naming the token it measures (`radius.lg · 18`). It points at real values, never at nothing.
2. **Two inks and a signal.** `fg-default` and `action-bg` carry the page. `signal-bg` appears only where something changed or is moving through the workflow. More than three orange marks on a screen is too many.
3. **Borders, not shadows.** Surfaces get a `stroke-hairline` in `border-default`; interactive elements a `stroke-ink` in `border-strong`.
4. **One surface.** The page is plain paper (`bg-canvas`), without grid lines. Grid paper (`bg-grid` at a `space-4` pitch on `bg-subtle`) appears only where something is literally being inspected: the redline stage and the card's stage variant. Never as a page, panel or section background (a test checks the components).
5. **The well is decoration.** The gravity well of the landing page (a polar mesh swirling into a hole, with cubes, spheres and dust in orbit) labels nothing and tells no story; the copy does. It is drawn from the `well-*` tokens, fades into the plain surface before any content starts, and stands still under `prefers-reduced-motion`.
6. **AAA.** Text reaches 7:1 on its ground in both themes (4.5:1 for large text, 24 px or 18.66 px bold), measured over the effective background; edges and the signal line reach 3:1. The one exception is the redline label (`signal-fg` on `signal-bg`, 5.7:1): no orange can be a 3:1 line on paper and carry 7:1 text at once. A test checks the token pairs; a browser test checks the rendered pages.
7. **Motion against change blindness.** Every change a person should notice is transitioned, never instant: what appears comes from where it comes from and goes back there, content that changes in place crossfades, a changed value is briefly highlighted in `action-subtle`, and layout moves instead of jumping. Short and functional, on the [motion tokens](/design-system/tokens/motion/) (no bounce, no decoration beyond the well). Under `prefers-reduced-motion` nothing moves and changes are instant, but changed values are still highlighted: that is information, not motion. The rule, with do and don't: [Motion](/design-system/motion/).

## Voice

Plain, specific, calm. Short sentences. Name the thing: "1 rename: color.cta → color.action", not "Some changes were detected". Commands are shown as command chips you can copy (`$ npm create dta` with a copy icon that turns into a tick), the same component everywhere; the chip, not a blue button, is the call to action. Designers and engineers are addressed equally; never "simply" or "just".

## Patterns

- **Severity without colour.** The system has no error colour, and `signal` is never used for errors (it means "changed"). Severity is a word plus a marker shape in the ink: an error is a **filled square**, a warning an **open ring**, a clean result the pass dot in `success-fg`. The [Findings](/design-system/components/findings/) list and its rule rows use it; a selected line turns its marker `action-text`.
- **A workspace, not a stacked page.** A tool that needs input first gives the page to the input ([Token input](/design-system/components/token-input/)); once something is loaded the input collapses into a [Source bar](/design-system/components/source-bar/) (a View Transition), a [Summary line](/design-system/components/summary-line/) stays visible, and the views are [Tabs](/design-system/components/tabs/) (sticky on phones, the selected one in the URL hash). Summaries first: lists show counts and open to their lines.
- **Side panel / bottom sheet.** Details of a selected row open in the [Detail panel](/design-system/components/detail-panel/) so the view behind stays in place: beside the view from 1024 px (non-modal, sticky), as a bottom sheet below (a modal native `<dialog>`, the page veiled with the canvas). Focus moves to the panel and returns to the row that opened it; Escape closes it. The panel comes in from the right, the sheet slides up from the bottom, and both go back the way they came. No modal dialogs for the views themselves.
- **Files to take away.** Generated files are listed, not dumped: [Output options](/design-system/components/output-options/) above them choose what is built, [Output files](/design-system/components/output-files/) group them by kind with one download per group and Copy and Download per file, a file's text opens in the Detail panel, and one primary "Download all" gives everything in the folders the CLI writes. Copy is the [Copy button](/design-system/components/copy-button/), Download a quiet Button next to it. Downloads are made in the browser (nothing is uploaded), and the way back to the CLI is the [CLI hand-off](/design-system/components/cli-handoff/): the generated config and the commands as command chips.
