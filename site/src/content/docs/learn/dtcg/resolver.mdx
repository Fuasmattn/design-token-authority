A token often has more than one value: one per brand, per light or dark theme, per breakpoint. The [Resolver module](https://www.designtokens.org/tr/2025.10/resolver/) describes those contexts without copying whole token files. It is a separate document, by convention `*.resolver.json`, that points at ordinary token files.

## Sets, modifiers and the resolution order

A resolver document has three parts:

- **`sets`**: named lists of token sources (files via `$ref`, or tokens written inline). A set is always applied.
- **`modifiers`**: named choices, each with **`contexts`** (one list of sources per option) and an optional **`default`**. `theme` with `light` and `dark` is a modifier; so is `brand`.
- **`resolutionOrder`**: the order in which sets and modifiers are applied. When the same token appears twice, **the later one wins**.

A tool resolves tokens for an **input** that picks one context per modifier, such as `{ "brand": "brandB", "theme": "dark" }`. A modifier without a `default` must be given. A shortened example (file names are illustrative):

```json title="tokens.resolver.json (DTCG 2025.10, not read by DTA yet)"
{
  "version": "2025-10-01",
  "sets": {
    "primitives": { "sources": [{ "$ref": "primitives.json" }] }
  },
  "modifiers": {
    "brand": {
      "contexts": {
        "brandA": [{ "$ref": "brand/a.json" }],
        "brandB": [{ "$ref": "brand/b.json" }]
      }
    },
    "theme": {
      "contexts": {
        "light": [{ "$ref": "theme/light.json" }],
        "dark": [{ "$ref": "theme/dark.json" }]
      },
      "default": "light"
    }
  },
  "resolutionOrder": [
    { "$ref": "#/sets/primitives" },
    { "$ref": "#/modifiers/brand" },
    { "$ref": "#/modifiers/theme" }
  ]
}
```

For `{ "brand": "brandB", "theme": "dark" }` the tool applies the primitives, then `brand/b.json`, then `theme/dark.json`; a token defined in both brand and theme files takes the theme value. The spec recommends keeping modifiers independent of each other ("orthogonal") where possible, and a modifier may not refer to another modifier.

:::note
The 2025.10 text gives two values for `version` (`2025-10-01` in the property table, `2025-11-01` in section 4.1.2). Check the current text before you rely on one.
:::

## The same ideas in DTA

DTA uses Figma's model, which carries the same information in file names:

| Resolver module                  | DTA (and Figma variables)                                                 |
| -------------------------------- | ------------------------------------------------------------------------- |
| a set                            | a collection with one mode: `Primitives.Value.json`                       |
| a modifier                       | a collection with several modes: `Brand.BrandA.json`, `Brand.BrandB.json` |
| a context                        | a mode                                                                    |
| an input                         | a mode listed in `brands` in `dta.config.ts`, built into one theme file   |
| `resolutionOrder`, last one wins | not needed: a token name exists in one collection only                    |

Two differences follow from that:

- **No overriding by order.** In the resolver a theme file can replace a brand token. In DTA each token belongs to one collection, and the other layers reach it through aliases. Overrides are modelled as their own tokens; see [Component overrides](/learn/patterns/component-overrides/).
- **One modifier per theme file.** DTA builds one CSS file per listed mode and does not combine two multi-mode collections (brand × theme) into every pairing yet; a set with both needs one mode per combination. See [Light and dark](/learn/patterns/themes/).

Reading and writing resolver documents is part of TICKET-094, as is Figma's native DTCG export (TICKET-032).
